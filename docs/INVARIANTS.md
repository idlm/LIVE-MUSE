# 连续录制不可违背原则（Muse 版）

这些原则来自 Live.Monitor V2 FullSpec。Muse 的所有判断都必须服从它们。

---

## 1. 录制连续性优先

只要用户已获得合法、有效的媒体流，且直播仍在进行：

- 优先保持录制，不因一次接口异常、入口状态变化、临时风控而停止。
- 允许断流期间形成缺口；恢复后尽快继续，并记录缺口原因。
- 不因“页面提示粉丝房/密码/限区”就停止仍然健康的媒体流。

## 2. 区分“入口状态”与“媒体健康”

| 状态 | 是否停止录制 |
|---|---|
| 页面提示粉丝/密码/限区，但 ffmpeg 仍在写媒体 | **不停止** |
| 平台 API 拒绝新取源，但 LKG 旧媒体仍健康且已授权 | **可继续（含旧源）** |
| 旧媒体失效 + 平台明确拒绝 + 无授权 | **停止，不绕过** |
| 超时/DNS/TLS/5xx/临时无读数 | **不停止，退避重试** |
| 明确下播（平台/watcher 确认） | **完成收尾，等下一场** |

## 3. 600 秒不是失效期限

- 600 秒只是 LKG 复用的**优先级参考**。
- 超过 600 秒的源仍必须通过媒体探针验证；验证健康就可以复用。
- 验证失败不删除历史源，只增加失败计数。

## 4. 恢复顺序

1. 当前正在使用的源
2. 目标画质的历史有效源
3. 其他画质的历史有效源
4. 主清单
5. 重新探测/平台取源

每一级都必须验证实际媒体；不能只看“地址存在”。

## 5. 明确下播与未知必须分开

- `403/401`、`needFan/needPassword/needCoinPurchase`、DRM、失效授权 = 明确拒绝。
- 超时、DNS、TLS、5xx、连接重置、风控 = 本次无读数，不等于下播。
- 只有平台/watcher 在本次录制开始后明确报离线，才按完成收尾。

## 6. 一个主播最多一个 owner

- 不得因为“确认一下”启动第二个录制器。
- 并发上限触顶时，自动录制排队；手动录制报错。
- 崩溃恢复时，进程身份无法核实 → 不杀、不并发写，升级用户。

## 7. 崩溃恢复保护已有内容

- 使用 `rec-checkpoints.json`。
- 原目录、原文件名前缀、`max(已有段号)+1` 继续。
- 旧文件不覆盖。
- 缺口写入 `gaps[]`，不伪造补录。
- 正常退出会清空检查点；崩溃才恢复。

## 8. 不绕过限制

不尝试：

- 猜密码/暴力密码
- 盗用/共用 Cookie
- 伪造 token/签名/请求
- 解密 DRM
- 绕过粉丝、付费、成人、地区限制
- 通过旧源获取当前未授权的媒体

旧源复用的边界：**之前已经通过合法授权取得，且当前仍能正常输出媒体**。

## 9. 请求节制

- 不因一次失败重复打整条取源链。
- 快速退避：10s→20s→40s→…封顶 5 分钟，前 10 次。
- 之后每 5 分钟慢速探测，约 24 小时上限；明确下播即停止。
- 不并发轰炸平台；不绕过按站车道/风控冷却。

## 10. 资源与磁盘

- 磁盘低于阈值：停止启动新任务，保留已有录像。
- 写盘失败（ENOSPC/只读/权限）：按 `disk` 收尾，不进入源失效重试。
- 并发上限：0=不限；超出时自动排队，手动报错。
- 不删除录像来“腾空间”，除非用户明确授权。

## 11. 可观测与脱敏

- 每次异常必须有：时间、房间、平台、状态、证据、动作、建议。
- 不输出 Cookie、token、完整签名 URL、密码。
- `lkg-sources.json` / `rec-checkpoints.json` 含地址，报告只引用字段，不贴原文。
- 不虚构测试/长稳结果。

## 12. 不确定时

**优先保护健康的录制。**  
不要停、不要重启、不要重复启动；先收集证据并升级用户。
